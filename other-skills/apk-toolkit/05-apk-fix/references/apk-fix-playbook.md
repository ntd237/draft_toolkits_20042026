# APK Fix Playbook — Diagnostic Buckets & Targeted Patches

Reference table for `05-apk-fix` (and triage classification reused by `04-apk-bugfinder`). Each bucket maps observed failure signals to the surgical patch and its limits. Backend attestation failures are `manual` and never patched.

### Auth Preservation Recipes (Firebase apps, re-signed builds)

Apply when authentication fails after a re-sign with a fresh keystore. Only proceed after the curl discriminator in `04-apk-bugfinder` confirms the endpoint accepts the client-side path.

**R1 — Original-cert SHA-1 spoof (`auth-cert-spoofable`)**: locate the obfuscated cert provider supplying the package signature to Firebase (grep smali for `getPackageInfo` + `GET_SIGNATURES`/`GET_SIGNING_CERTIFICATES` feeding a `[B` return; class was `pb.1.a`, method `a(Landroid/content/Context;Ljava/lang/String;)[B`). Rewrite the WHOLE method to return a hardcoded 20-byte array of the original cert SHA-1 (obtain from the original APK via `apksigner verify --print-certs`), filled via `const/16 v0, 0x14` + `new-array` + `fill-array-data` (note: `const/4` cannot hold 0x14). Every Firebase component (Auth, FIS, App Check) then sends the original SHA-1 in `X-Android-Cert`.

**R2 — App Check client-fatal neutralization (`appcheck-client-fatal`)**: in `io/invertase/firebase/appcheck/ReactNativeFirebaseAppCheckModule.smali`, rewrite the static synthetic promise listeners `d`/`e` (getToken / getLimitedUseToken Task listeners) whole-method to always `Promise.resolve` a `WritableMap` `{token: "patched-appcheck-token"}` instead of rejecting. Descriptor must end `)V`. Valid ONLY when the target endpoint accepts requests without the header (curl-verified); endpoints enforcing App Check server-side remain blocked (`attestation` → manual).

**R3 — Cross-split drawable alias repair (`cross-split-alias-null`)**: 
1. Enumerate the damage: all `<item type="drawable" name="...">@null</item>` in `res/values/drawables.xml` + all `@null`-valued resource items in `styles.xml` (e.g. `android:src`) whose ORIGINAL value (from `aapt2 dump resources original.apk`) was a reference `@0x7f....`.
2. Build the alias→target map from the original base dump (each alias's value is a target resource ID), then resolve each target ID → name + file path using the dumps of the OTHER splits (the targets live in a split table, typically the density split).
3. **Decode the owning split with apktool** (`apktool d split_config.xxxhdpi.apk`) and copy the decoded TEXT XML / bitmap files into base res under the ALIAS names (`res/drawable-anydpi*/<alias>.xml`, bitmaps → `res/drawable-xxxhdpi/<alias>.png`). NEVER raw-extract files from the split APK — they are compiled binary AXML that apktool cannot rebuild.
4. Materializing under the ALIAS names (not the target names) adds NO new resource names/IDs → no base/split table conflicts. Keep the existing resource IDs stable.
5. Remove the corresponding `@null` `<item>` lines from `drawables.xml`; replace nullified style items with `@drawable/<alias>`.

**R4 — Server-owned state override (`server-owned-state`)**: 
1. Trace the toggle's write path in the decompiled JS: the handler calls a backend profile-update (e.g. `changeProfileInfo({badge: <CONST>})`), then `updateCurrentUser` ONLY on success; the periodic user refetch later replaces the whole local user object → server value wins.
2. Find the client-side DERIVATION predicate the UI uses to render the state (e.g. `doesUserHaveGoldBadge(value)` comparing `value === 'CONST'`); all badge/toggle/avatar rendering flows through it.
3. Patch the predicate's function body in Hermes bytecode to return true unconditionally: overwrite its first instructions with `LoadConstTrue <reg>; Ret <reg>` (opcodes from the hermes-dec v96 table: LoadConstTrue=120/0x78, Ret=92/0x5C; operands Reg8). Verify the function's exact bytes first, and confirm the function is tiny (a 16-byte body → remaining bytes become unreachable dead code after Ret).
4. The backend call in the write path still fires on manual toggle and the server may still reject it — with the predicate patched, the rejection is silently absorbed (analytics only). Do NOT attempt to forge the server call itself (`attestation`-class scope).
5. Verify persistence: state must survive BOTH the original auto-revert window (observe ≥ the window measured during reproduction) AND a fresh force-stop relaunch — assert via pixel/UI metrics, never via a single immediate screenshot.

**Smali rewrite pitfalls (learned the hard way — all caused corrupt dex or runtime errors)**:
- NEVER splice instructions mid-line or mid-block: produces a dex that assembles but starts with zero bytes → runtime `NoClassDefFoundError`. Always rewrite the complete method block, preserving the file's exact line endings (CRLF in this tree).
- Regex replacements matching repeated labels (`:cond_0`) overpatch unrelated methods — slice replacements by method block boundaries (`.method` … `.end method`), never by global regex.
- `WritableMap.putString` returns `V`, not `Ljava/lang/Object;` (unlike `Map.put`) — wrong descriptor → `NoSuchMethodError`.
- Verify each rebuilt dex: correct size, starts with `dex\n` magic, and `dexdump`/install succeeds before shipping.
- Use apktool ≥ 2.11.1: it restores `META-INF` on rebuild; 2.10.0 does not → `kotlinx-coroutines` Main dispatcher crash at startup.

### 4 Client-Side Paid-Unlock Techniques (Reference for `decision-point-miss`)
1. **Patch the decision point directly in Hermes bytecode**: disassemble `index.android.bundle` with `hbctool`/`hermes-dec`, locate the function handling the backend user response (where the subscription state is read), and force it to always return "Gold = true" / a truthy value, then reassemble (or patch the operand bytes directly). Result: right after login, even when the backend reports "free", the app renders the paid edition. No purchase, no restore.
2. **Hook the native bridge module at smali level**: instead of editing the JS, patch the native module feeding data to JS (the app's API/purchases module) to forge the response before it reaches JS. Equivalent effect; slightly harder to detect.
3. **Forge the local RevenueCat cache**: the RevenueCat SDK caches CustomerInfo on disk and emits it to listeners at startup; a modded build ships a forged cache pre-loaded with an active entitlement — activated at startup instead of waiting for a purchase flow.
4. **Backend proxy/MITM** (rare; only when features are gated server-side): repack the app + strip cert pinning + forge API responses — **lab-only per the two-tier doctrine (README Hard Rule 3)**: requires explicit spec opt-in, external proxy infrastructure outside the deliverable, and verbatim `PATCH_REPORT.md` disclosure; never bypasses platform attestation (`bypassable: false` stays untouchable) and is never bundled into the portable deliverable.

## Escalation Rules
1. **Snapshot before every patch**: `work/verify/snapshot-iter-<N>/`; roll back on assembly failure or syntax regression.
2. **Two-strike rule**: 2 consecutive failures in the identical bucket → halt blind patching and re-route to `04-apk-bugfinder` (mandatory, not optional).
3. **Iteration cap**: 2 total fix iterations per RCA round; at the cap re-route to `04-apk-bugfinder` with full `fix-history.md` evidence — a further attempt requires a NEW RCA handoff.
4. **Manual bucket firewall**: never consume fix iterations on `auth-firebase`, `attestation`, or `incomplete-input` buckets; report immediately.
5. **Keystore invariant**: always re-sign with the SAME fresh keystore `03-apk-implement` generated; both v1 and v2 schemes enabled; bump `versionCode` per rebuild.

## Patch Hygiene
- Tag every edit `// FIX iter-<N>: <reason>`.
- Prefer restoring original bytes (`original.apk`) over hand-editing corrupted regions.
- After restore-based patches, re-apply only the conversion patches documented in `PATCH_REPORT.md` that touch the restored files.
- **Byte-level patch verification**: after any binary patch (Hermes bundle, .so, dex), diff against the pre-patch snapshot and assert ONLY the intended bytes changed (`diff offsets` must equal the documented set); verify the patch survives the rebuild by re-extracting the artifact from the rebuilt APK and re-checking the bytes.
- **Toolchain pin**: verify `java -jar <apktool.jar> --version` before every rebuild; in this workspace the ONLY blessed jar is `work/tools/apktool.jar` (2.11.1). A rebuild that emits an APK with 0 `META-INF/` entries is silently broken — always assert `META-INF` entry count > 0 before signing.
- **`@null` diff gate (MANDATORY after every resource-affecting rebuild)**: dump resources of the ORIGINAL base (`aapt2 dump resources original.apk`) and of the rebuilt artifact; enumerate every resource whose value is `@null`. Any name present in the rebuilt dump but NOT in the original (or originally a resource reference `@0x7f...`) = a nullified alias introduced by base-only decode → apply Recipe R3 BEFORE signing. A rebuilt APK is not shippable while this diff is non-empty.
- **Server-verdict isolation rule**: when patching a client-side state to bypass a server-owned flag, the UI must NEVER depend on the server's response to that flag. Patch the derivation predicate (R4), not the network call; if the write path surfaces errors to the user (toasts/dialogs), neutralize those surfaces too. Never block or fake the server request itself — silently absorbed rejection is the intended design.
- **Persistence-then-verify rule**: any patched state that previously reverted on server sync must be verified over TIME (≥ the observed auto-revert window) and across a fresh process restart, not just immediately after the toggle.
